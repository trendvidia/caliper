# GoCaliper

Semantic code analysis and transformation tool for Go, inspired by [Coccinelle](https://coccinelle.lip6.fr/). GoCaliper runs as an [MCP](https://modelcontextprotocol.io/) server, exposing AST-level pattern matching, control flow analysis, and code transformation to LLM-powered tools.

## Install

```bash
brew install trendvidia/tap/gocaliper --head
```

Or build from source:

```bash
go install github.com/trendvidia/gocaliper/cmd/gocaliper-mcp@latest
```

## Claude Code MCP Configuration

Add GoCaliper to your Claude Code settings (`~/.claude/settings.json`):

```json
{
  "mcpServers": {
    "gocaliper": {
      "command": "gocaliper",
      "args": []
    }
  }
}
```

Or for a project-specific setup, add to `.claude/settings.json` in your repo root.

If you installed via `go install` instead of Homebrew, use the full path:

```json
{
  "mcpServers": {
    "gocaliper": {
      "command": "/path/to/go/bin/gocaliper-mcp",
      "args": []
    }
  }
}
```

## Tools

GoCaliper exposes the following MCP tools:

**Pattern Matching**
- `find_pattern` — match code using AST patterns with metavariables
- `find_type_usage` — find all usages of a specific type
- `list_equivalences` — show semantic equivalences used in matching

**Control Flow Analysis**
- `find_resource_leak` — detect missing cleanup on code paths
- `find_unchecked_error` — find ignored/unchecked errors
- `find_lock_violation` — detect mutex discipline violations
- `find_nil_deref` — find nil pointer dereferences
- `check_path_property` — generic path property checker

**Code Transformation**
- `apply_transform` — rewrite code matching a pattern
- `migrate_api` — multi-rule API migrations with import updates
- `add_missing_cleanup` — auto-insert missing defer statements

**Advanced Analysis**
- `find_goroutine_leak` — detect leaked goroutines
- `find_sql_injection` — find SQL injection vulnerabilities
- `find_race_condition` — detect data races in concurrent code
- `find_context_misuse` — find context.Background() misuse
- `find_taint_flow` — trace untrusted data to sensitive sinks
- `find_call_sites` — find all callers of a function

**Pattern Language**
- `run_patterns` — load and execute .gcl rule files against a codebase

**Debugging**
- `explain_match` — debug why a pattern did/didn't match

## LLM-Effective Usage

GoCaliper's MCP tools are designed so that an LLM never writes formal logic — each tool encapsulates the formal reasoning (CTL model checking, path quantifiers, CFG traversal) behind an intent-based interface.

### What works well via LLM

| Capability | How the LLM uses it |
|---|---|
| Pattern finding | "find all Close() calls" → `find_pattern` with `$x.Close()` |
| Type exploration | "where is `*sql.DB` used?" → `find_type_usage` |
| Refactoring | "rename OldFunc to NewFunc" → `apply_transform` |
| Bug detection | "any resource leaks?" → `find_resource_leak` |
| Migration | "upgrade from v1 to v2 API" → `migrate_api` with rules |
| Validation | "test this pattern" → `explain_match` + iterate |
| Policy enforcement | "run our team's rules" → `run_patterns` |

### What's better left to humans

- Authoring complex `.gcl` rule files with `absent`/`contains` logic
- Writing `.gsp` semantic patches with multi-rule dependencies
- Configuring CI gates and choosing severity thresholds
- Defining organizational coding policies

### LLM as Policy-to-Rules Translator

The most powerful workflow combines both: **humans write policy documents, the LLM translates them into enforceable rules.**

Given a policy document (e.g., `POLICIES.md`) and access to the codebase via MCP tools, an LLM can:

1. **Read the policy** — understand natural language requirements ("all database connections must be closed", "never log PII fields", "context.Context must be first parameter")

2. **Explore the codebase** — use `find_pattern` and `find_type_usage` to learn naming conventions, package structure, and existing patterns

3. **Generate `.gcl` rules** — translate each policy into pattern rules:
   ```
   # Generated by LLM from POLICIES.md § 3.2
   version = 1
   name = "db-safety"
   patterns = {
     open_db: { pattern = "$db, $err := sql.Open($args...)" }
     close_db: { pattern = "$db.Close()" }
   }
   rules = [{
     name = "unclosed-db-connection"
     severity = "error"
     match = "@open_db"
     absent = "@close_db"
     message = "Database connection opened but never closed"
   }]
   ```

4. **Validate the rules** — use `run_patterns` to test against the codebase, check for false positives, refine patterns

5. **Generate CI configuration** — produce `.gocaliper.pxf` config, GitHub Actions workflow, or other CI gate setup

This workflow means:
- **Policy authors** write natural language (in a wiki, RFC, or markdown file)
- **LLM** translates to machine-enforceable rules (one-time or on policy change)
- **CI** runs the rules on every PR (no LLM in the loop)
- **Developers** see actionable findings with clear messages tied back to policy

### Example: Full Policy Enforcement Pipeline

```
POLICIES.md (human-authored)
    ↓
LLM reads policies + explores codebase (via MCP tools)
    ↓
patterns/*.gcl (LLM-generated, human-reviewed)
    ↓
.gocaliper.pxf (points to pattern files)
    ↓
CI: gocaliper check --diff (runs on every PR)
    ↓
SARIF → GitHub Code Scanning (findings in PR review)
```

The LLM acts as a bridge between human intent and machine enforcement. It only needs to run once (or when policies change) — the resulting `.gcl` files are deterministic and run without an LLM.

## Configuration

GoCaliper uses PXF format (protowire) for configuration. Create `.gocaliper.pxf` in your project root:

```
severity = {
  resource_leak: "error"
  unchecked_error: "warning"
}
rules {
  enable = ["resource_leak", "unchecked_error"]
}
engine {
  skip_generated = true
  build_tags = ["integration"]
}
patterns = ["patterns/*.gcl"]
```
